# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.0.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## Unreleased
### Added
- Added an optional `dimension_key` parameter to `cost-explorer` `getDimensionValues`: with `dimension` `PRODUCT_ATTRIBUTE` it lists the values of one product attribute (such as `model`) instead of the attribute names. The description now documents `ProductAttributes` filter leaves and `PRODUCT_ATTRIBUTE` grouping for Amazon Bedrock costs, including that keys and values are case-sensitive, a wrong value returns $0 rather than an error, and data starts on 2026-09-01. (#4990)
- Added `attachment_state` (`Attached` or `Unattached`) to `cost-optimization` `get_recommendation` responses for EBS volumes, so a `Delete` recommendation for an idle attached volume can be told apart from one for an unattached volume. (#4966)
- `bcm-pricing-calc` `list_workload_estimates` `status_filter` now also accepts a list of statuses (or a JSON array string), returning estimates in any of them in one call instead of one call per status. Entries are matched case-insensitively and repeats dropped, every unknown entry is named in one `validation_error`, and an empty list is rejected; a single status string works as before. (#4959)
- Added `decimal_values` to each row of `list-billing-group-cost-reports` and `get-billing-group-cost-report`: `aws_cost`, `proforma_cost`, `margin` and `margin_percentage` written in plain decimal notation with every digit kept, since the service can return them in exponent form (`"5.0E-7"`). The original string fields are unchanged. (#4958)
- Added `receiver_role` (`SELLER`, `RESELLER` or `BUYER`) to `invoicing` `list_invoice_summaries`: it returns only invoices where the account holds that role, raises the date-range limit from one month to less than five years, and is the only way to get estimated invoices (`InvoiceId` starting with `Estimate-`); it cannot be combined with `invoice_id`. Responses now include `data.selector`, the account or invoice the query ran for and whether the account was auto-detected, since rows for invoice-unit receivers carry a different `AccountId`. The description now lists the fields the API returns and warns that `CREDIT_MEMO` amounts are positive and `PAYMENT_RECEIPT` rows are not charges, and `invoice-units` documents `Rule.BillSourceAccounts`. (#4925)
- Added `period_note` to MONTHLY results whose periods differ from the requested dates: `cost-explorer` `getCostForecast` and `getUsageForecast` (whole calendar months are returned, and a month already under way includes actual spend to date), and the Savings Plans and Reserved Instance utilization results of `cost-explorer`, `sp-performance` and `ri-performance` (entries are labelled with the whole month but hold only the requested days). `ri-performance` responses also echo the request as `requested_time_period`. (#4919)
- Added a read-only `budget-performance-history` tool (`DescribeBudgetPerformanceHistory`) that returns, for one budget, the budgeted and actual amount of each past period, oldest first, to answer which months went over budget. It covers DAILY, MONTHLY and QUARTERLY budgets; a CUSTOM or ANNUALLY budget returns a `validation_error`. (#4913)
- Added `get_account_plan_state` and `list_account_activities` operations to the `free-tier-usage` tool, for accounts on the Free or Paid plan introduced on July 15, 2025. `get_account_plan_state` returns the plan type and status, remaining Free Tier credits and expiration date, or `plan_record_found: false` for an account with no plan record (such as an older account on the legacy Free Tier); `list_account_activities` lists the activities that earn Free Tier credits, with each one's status and reward. (#4912)
- Added a read-only `cost-anomaly-monitors` tool (`GetAnomalyMonitors`, `GetAnomalySubscriptions`) with `list_monitors` and `list_subscriptions` operations, showing what each Cost Anomaly Detection monitor tracks and which alert subscriptions notify whom, how often, and at what impact threshold. An optional `monitor_arn` returns only that monitor, or only the subscriptions attached to it, and results page with `max_items` and `next_token` like the other paginated tools. (#4911)
- Added `found_in_region` (when exactly one region returns the event) and `regions_not_found` to multi-region `compute-optimizer-automation` `list_automation_event_steps` responses, and `regions_queried` to a successful multi-region `get_automation_event`. Both fields are kept when a large response is offloaded to SQL. (#4963)
- Added `total_recommendation_count` to Cost Optimization Hub `list_recommendation_summaries` responses: the sum of the groups' `recommendation_count`, so the overall count no longer has to be added up by the caller. It is included only when every group was fetched, and left out on a partial result, a continuation call, or when a group has no count. (#4934)
- Added `retry_strategy` (`retry_same_request`, `modify_request`, or `do_not_retry`) and, where a fixed next action exists, `hint` to every tool error response, derived centrally from `error_type`. Existing `error_type` values and fields are unchanged. Tools can override both via new `retry_strategy=` / `hint=` arguments on `format_response`. See "Error responses" in the README.
- Added tag support to the Cost Optimization Hub tool. `list_recommendation_summaries` accepts `group_by='TagKey:<tag key>'` to group recommendations by a tag's values (e.g. `TagKey:Environment`); recommendations without the tag are grouped under `NoTagKey`. The `TagKey:` prefix is matched case-insensitively, the tag key is kept as given, and a `TagKey:` with no key is rejected with a `validation_error`. The `tags` filter (`[{"key": ..., "value": ...}]`) is now documented for `list_recommendations` and `list_recommendation_summaries`: values for the same key are ORed, different keys are ANDed, and matching is exact. `Key`/`Value` field names are folded to `key`/`value`, and a single tag object is wrapped in a list.
- Added a read-only `get-billing-transfer-preference` tool to AWS Billing Conductor (`GetBillingTransferPreference`) reporting whether, in a two-level billing transfer, a billing group is created automatically for the indirect relationship with each new end customer, the pricing plan applied to those billing groups, and when the preference was last changed
- Added an optional `cpu_vendor_architectures` parameter to the AWS Compute Optimizer `get_ec2_instance_recommendations`, `get_auto_scaling_group_recommendations`, and `get_rds_recommendations` operations to request Graviton recommendations. It takes a JSON array (or a single value) of `CURRENT` and/or `AWS_ARM64`, matched case- and underscore-insensitively, and is sent as `recommendationPreferences.cpuVendorArchitectures`; without it the API ranks options within the current CPU architecture. The response echoes the preference as `applied_recommendation_preferences`. Other operations reject the parameter with a structured `validation_error`, as do values outside `CURRENT`/`AWS_ARM64`.
- Added an optional `resource_arns` parameter to the `compute-optimizer` tool to look up recommendations for specific resources. It is sent as each operation's ARN filter (`instanceArns`, `autoScalingGroupArns`, `volumeArns`, `functionArns`, `serviceArns`, or `resourceArns` for RDS and idle), so a single resource no longer requires paging the full recommendation list. A single bare ARN is accepted as well as a JSON array. The region is taken from the ARNs when `region` is omitted; ARNs spanning multiple regions, or in a different region than `region`, are rejected.
- Added an optional `order_by` parameter to the AWS Compute Optimizer `get_idle_recommendations` operation (`{"dimension": "SavingsValue"|"SavingsValueAfterDiscount", "order": "Asc"|"Desc"}`, matched case-insensitively). Idle results now default to `SavingsValueAfterDiscount` descending, so the first page holds the largest savings. Other operations reject `order_by` rather than ignore it.
- Added more fields to the AWS Compute Optimizer recommendation responses, including finding reason codes, current performance risk, inferred workload types, migration effort, GPU info, savings after discounts, utilization metrics, lookback period, and effective recommendation preferences, plus Auto Scaling group capacity, EBS volume configuration, and RDS cluster and storage details. The EC2, Auto Scaling group, EBS, RDS, and ECS responses now also carry the API's response-level `errors` list (Lambda's API has none).
- Added `list-billing-view-segments` tool wrapping the read-only `billing:ListBillingViewSegments` API, which lists billing view segments over a time period — each segment identifies the billing domain (BILLABLE or PRO_FORMA) and the account relationships (management account, billing group, billing transfer) that applied during its time range
- Added AWS Billing preferences support via a read-only `get-billing-preferences` tool (`GetBillingPreferences`) reporting which member accounts participate in the Reserved Instance / Savings Plans discount pool and in credit sharing, whether newly created accounts join automatically, whether sharing is open, whether billing alerts are enabled, and the per-billing-period history of those settings. This is the only source for an account's discount-sharing state
- Added AWS Billing Business Support data via a `business-support` tool (`ListBusinessSupportAccountCharges`, `ListBusinessSupportSubscriptionHistory`) covering a billing month's per-account Business Support charges with the Support-eligible spend, tiered charge breakdown, discounts and profile-wide totals (estimated for the current month), and the Support plan contract history for a month or date range. Billing months before 2024-01 and future months are rejected locally, and large results are offloaded to session SQL with one row per charge or contract (#4840)
- Added AWS Billing Enterprise Support data via an `enterprise-support` tool (`GetEnterpriseSupportChargeSummary`, `GetEnterpriseSupportContractDetails`, `ListEnterpriseSupportLinkedAccountCharges`) covering a billing period's Enterprise Support charge and the Support-eligible spend it was calculated from, the contract terms that govern how the charge is allocated, and the per-linked-account charge breakdown
- Added additional reservation cost and savings metrics to `get_reservation_utilization`: `on_demand_cost_of_ri_hours_used`, `net_ri_savings`, `total_potential_ri_savings`, `amortized_upfront_fee`, `amortized_recurring_fee`, `total_amortized_fee`, `ri_cost_for_unused_hours`, `realized_savings` and `unrealized_savings`.
- Added AWS Billing credits support via a `credits` tool (`GetCredits`, `GetCreditAllocationHistory`) covering credit balance, expiration, product applicability, sharing configuration, and the per-service allocation ledger
- Added AWS Compute Optimizer Automation support via a `compute-optimizer-automation` tool (`GetAutomationEvent`, `GetAutomationRule`, `GetEnrollmentConfiguration`, `ListAccounts`, `ListAutomationEvents`, `ListAutomationEventSteps`, `ListAutomationEventSummaries`, `ListAutomationRules`, `ListRecommendedActions`, `ListRecommendedActionSummaries`, `ListAutomationRulePreview`, `ListAutomationRulePreviewSummaries`, `ListTagsForResource`)
- Extending support for Billing and Cost Management Pricing Calculator's Workload estimate (`CreateWorkloadEstimate`, `BatchCreateWorkloadEstimateUsage`).
- Added AWS Billing Conductor tools to analize billing groups, account associations, billing group cost reports, pricing rules/plans, and custom line items
- Added AWS Billing tools for managing and querying billing views
- Added optional `billing_view_arn` parameter to 7 Cost Explorer operations to scope queries to specific billing views (PRIMARY, BILLING_GROUP, CUSTOM, BILLING_TRANSFER, BILLING_TRANSFER_SHOWBACK)
- Added local time-filter validation to the AWS Invoicing `list_invoice_summaries` operation so requests the service cannot satisfy are refused before the round trip: ranges longer than one month, reversed or empty ranges, and a missing time filter on the account selector. An over-long range returns `suggested_date_ranges`, the per-month sub-ranges that together cover the request, expressed as dates rather than billing periods to preserve issued-date semantics. The span limit follows the number of days in the start date's month (28 from a February start, 31 from a January one) rather than a flat 31 days.
- Added AWS Compute Optimizer idle-resource support via a new `get_idle_recommendations` operation on the `compute-optimizer` tool (`GetIdleRecommendations`), with server-side filtering by `Finding` (`Idle`, `Unattached`, `Unused`) and `ResourceType`. The formatted response includes resource ARN/ID/type, account, finding and finding description, both savings-opportunity variants, utilization metrics, lookback period, last-refresh timestamp, tags, response-level errors, and the pagination token.
- Added `current_resource_details` to the Cost Optimization Hub `get_recommendation` response (alongside the existing `recommended_resource_details`).
- Added AWS Cost Optimization Hub efficiency-metrics support via a new `list_efficiency_metrics` operation on the `cost-optimization-hub` tool (`ListEfficiencyMetrics`), reporting per-account or per-Region efficiency score, savings, and spend over a Daily or Monthly window. Supports `granularity`, `start_date`/`end_date` (with automatic clamping into the API's 90-day Daily / 3-month Monthly lookback), `group_by` (`AccountId` or `Region`), `order_by`, and pagination, and offloads large responses to session SQL.
- Added an `order_by` passthrough to the Cost Optimization Hub `list_recommendations` operation, forwarding the COH `orderBy` structure (`{"dimension": ..., "order": "Asc"|"Desc"}`) to sort recommendations server-side by any supported dimension.
- Added a `ranking_mode='performance'` option to the Cost Optimization Hub `list_efficiency_metrics` operation for "most efficient / top / worst performer" rankings of accounts or Regions. It fetches the highest-spend groups first, drops idle/no-score groups, then ranks by efficiency score — either the Pareto "vital few" (highest-spend groups making up ~80% of total spend) when the full set is retrieved, or the fetched top spenders (with a `ranking_focus` disclosure that only the top spenders were analyzed) when the fetch hits its page cap. Requires `group_by`; the `order_by` direction selects best-first vs. worst-first.
- Added `material_spend` and `material_spend_fraction` to the Cost Optimization Hub `list_efficiency_metrics` `ranking_focus` disclosure (`ranking_mode='performance'`), reporting the kept groups' combined spend and their actual cumulative share of total spend so callers state the real share instead of the ~80% selection cutoff. The fraction is `null` when the fetch hits its page cap (total spend then covers only the fetched top spenders, not the whole org).
- Added session SQL offload to the `sp-explorer` tool's offering operations (`DescribeSavingsPlansOfferings`, `DescribeSavingsPlansOfferingRates`): a result above the shared size threshold is stored as one row per offering or rate in a session SQLite table (queried with the `session-sql` tool) instead of returned inline, while a small result is returned inline unchanged
- Added session SQL offload to the `sp-explorer` tool's inventory and plan-rate operations (`DescribeSavingsPlans`, `DescribeSavingsPlanRates`): a result above the shared size threshold is stored as one row per plan or rate in a session SQLite table (queried with the `session-sql` tool) instead of returned inline, while a small result is returned inline unchanged. The `DescribeSavingsPlanRates` sentinel keeps the `savingsPlanId` the rates belong to
- Added a `list_enrollment_statuses` operation to the `cost-optimization-hub` tool (`ListEnrollmentStatuses`), returning the calling account's Cost Optimization Hub enrollment status (`Active`/`Inactive`) with created and last-updated timestamps, or that of the account given in the optional `account_id`. An account with no enrollment record (never enrolled) is reported as `Inactive` instead of an empty list.
- Added a `get_preferences` operation to the `cost-optimization-hub` tool (`GetPreferences`), returning the calling account's savings estimation mode, member account discount visibility, and preferred commitment (term and payment option).

### Changed
- The `cost-explorer` `getCostForecast` description now warns that forecasts made in the first days of a month are less accurate, because some services bill a large amount on or near the 1st and skew the early-month daily average, and that volatile spend also lowers accuracy. It tells the caller to check the prediction interval and compare with the last few months of actual cost before quoting a forecast, and, when large one-time charges such as Marketplace contracts or upfront fees drive the volatility, to forecast `BILLING_ENTITY` `AWS` separately and add those charges from recent actuals. Documentation only. (#5033)
- **Breaking:** the server now requires Python 3.11 or newer (previously 3.10), so upgrade Python before upgrading the server. The locked dependencies are also updated, including dnspython 2.9 for a security fix. (#4995)
- The Billing Conductor tools now say what they return for a month in which nothing was in effect: `list-billing-group-cost-reports` and `get-billing-group-cost-report` return an empty result, while `list-resources-associated-to-custom-line-item`, `list-pricing-rules-for-plan` and `list-pricing-plans-for-rule` fail with `ResourceNotFoundException`, the same error a mistyped ARN gets. (#4960)
- Raised the `boto3` floor to 1.43.110. Older botocore versions drop the `ProductAttributes` filter from budget responses, so a budget filtered by a product attribute came back with an empty `{}` node in its filter, which reads as unfiltered. (#4923)
- The `sp-recommendation` `filter` argument doc now says the `LINKED_ACCOUNT` `Dimensions` filter can be wrapped in a single `Not` to exclude accounts from a Savings Plans purchase recommendation, with an example; it previously said only that `And` and `Or` were unsupported. It also states that `MatchOptions`, if given, must be `EQUALS`, and that a `Not` inside another `Not` is not supported. (#4920)
- Cost Optimization Hub `list_recommendation_summaries` now rejects the `recommendationIds`, `resourceIds` and `resourceArns` filters locally with a `validation_error` listing `unsupported_filters` and `supported_filters`, instead of calling the API, which rejects each of them with a `ValidationException`. `list_recommendations` still accepts them. (#4934)
- `sp-explorer` `describe_savings_plans` now states that it returns the plans owned by the **calling account only**. `DescribeSavingsPlans` is scoped to the calling account, so from a management account it returns none of the plans its member accounts bought, even when asked for by id or ARN, and the `SavingsPlan` response shape carries no owner field to say so; the description previously said "The plans the account owns" without naming the account, which reads as organization-wide and leads a caller to take an empty list for "owns none". The description now names the organization-wide sources — `sp-performance get_savings_plans_utilization_details` (the owning account is the plan ARN's account field) and `cost-explorer getDimensionValues` for `SAVINGS_PLAN_ARN` under `context=SAVINGS_PLANS` — and asks for an explicit 12-month `start_date`/`end_date`, since both read Cost Explorer, which lists a plan only where it has utilization records in the window, and `get_date_range` defaults to 30 days. An empty `describe_savings_plans` result now carries a `message` saying the same thing, as `sp-performance`'s empty results already do, so it reaches a caller that does not re-read the description; a non-empty result is unchanged. `describe_savings_plan_rates` omits `savingsPlanId` when unset instead of sending `None`, so botocore names the missing required field rather than reporting a type error on its value. (#4856)
- **Breaking:** `ri-performance` `get_reservation_coverage` returns only `on_demand_cost` in `coverage_cost`. The `reserved_cost`, `total_cost` and `coverage_cost_percentage` fields are removed: Cost Explorer's `CoverageCost` has only `OnDemandCost`, so they were always `null`. Use `coverage_hours` (or `coverage_normalized_units` for EC2) for coverage percentages. (#4835)
- **Breaking:** `cost-optimization` `list_recommendation_summaries` now requests the `SavingsPercentage` metric, so `metrics.savings_percentage` carries the percentage (`'12%'`, clamped to `'>=80%'`/`'<=2%'`): the estimated deduplicated monthly savings as a percent of the last 30 days' net amortized cost, excluding credits and refunds, for the whole filtered result. It was previously always the service placeholder `Percentage not requested.`. When the service cannot compute it (savings estimation mode BeforeDiscounts, a filter other than `accountIds`, `regions` and `tags`, or a calculation failure), `metrics.savings_percentage` is absent and `metrics.savings_percentage_unavailable_reason` carries the service's text. `restartNeeded`/`rollbackPossible` filters given as `"true"`/`"false"` strings are coerced to booleans instead of failing botocore validation; summaries `group_by` values are matched case-insensitively (underscores are not ignored, so `RESOURCE_TYPE` is rejected). (#4987)
- **Breaking:** `sp-performance` now labels the request window `requested_time_period` instead of `time_period` on all three operations. A MONTHLY utilization entry's `TimePeriod` is labelled with its calendar month (a 2026-08-17 start returns a first entry labelled 2026-08-01, whose figures still start on the 17th), and the description now says so. `get_savings_plans_utilization_details` now returns the API's `TimePeriod` as `time_period` (the requested start, and an end the API may move earlier to the first day without complete data), and returns `total` only when the whole query came back in one page: the API's `Total` covers only the Savings Plans on its own page, so a multi-page, partial (`max_items`) or `next_token` continuation result previously reported one page's figure as the query's (live: page 1 of 3 reported 100% utilization against 99.71% for the query). `get_savings_plans_coverage` no longer reads a `Total` (the GetSavingsPlansCoverage API does not return one) and reports `granularity` only when it was sent, not with `group_by`. The description lists the utilization details filter dimensions and says which period to report. (#4806)
- **Breaking:** `ri-performance` grouped `get_reservation_coverage` and `get_reservation_utilization` return a period's `total` only when the whole query came back in one page. With `group_by`, the API's period `Total` sums only the groups on its own page, and the tool kept page 1's as the period's: live, a 3-group page of an 877-group coverage query reported 638,311 running hours against 902,438,217 for the query, and a `next_token` continuation reported its own page's 1,311,271. `total` is now omitted from a multi-page, partial (`max_items`/`max_pages`) or `next_token` continuation result, and the description points to the ungrouped call for the overall figure. A `total` the API did not return is omitted rather than returned as `{}`. Ungrouped results, which are always one page, are unchanged.
- **Breaking:** every paginated tool operation now takes `max_items` (the total number of items to return) and `next_token`. The `max_results`, `max_pages` and `page_size` parameters are removed (`ri-performance` keeps `max_pages` for `get_reservation_utilization`, below), and `next_page_token` (`sp-purchase-analyzer`, `sp-recommendation`) is renamed to `next_token`. Without `max_items` an operation fetches every page; with it, the operation stops before a page that could take the result past `max_items` (the first page is always returned) and returns the service's own continuation token unchanged. `ri-performance` `get_reservation_utilization` grouped by `SUBSCRIPTION_ID` takes `max_pages` (pages of 500 groups) instead of `max_items`, because its token only works with the same page size; `max_items` there returns `validation_error`. Billing Conductor `get-billing-group-cost-report` requests pages of 200 to 300 results, the range the service accepts, so a `max_items` below 200 can return up to 200. One call stops paging, on a page boundary, after `BCM_MCP_PAGINATION_MAX_SECONDS` (default 300) seconds. Paginated responses carry a lowercase `pagination` block (`complete_dataset`, `has_more`, `next_token`, `items_returned`) ahead of the data, inline and in the SQL-offload result; `has_more` is true only when there is a `next_token` to continue with, and `complete_dataset` reports whether the result is partial; a partial result also leads with top-level `complete_dataset: false` and a `warning`. The old `Pagination` block, top-level `next_token`, `has_more_results`, `total_count`, `pages_fetched`, `total_results` and `duration_ms` fields are removed. A rejected or expired `next_token` returns `error_type: invalid_next_token` (`retry_strategy: modify_request`). Operations that are not paginated take neither parameter. See "Pagination" in the README.
- **Breaking:** `utilities.aws_service_base.paginate_aws_response` is removed. Its replacement, `paginate_aws_items`, takes a `PageSpec` describing how the operation pages, plus keyword-only `max_items` and `next_token`, and returns `(items, pages, pagination)`. `with_pagination` and `first_page_fields` build the response.
- The session-SQL offload handle is now bounded: `preview` is capped at 4 KB with string cells, and the text form of other cells such as BLOBs, over 200 characters shortened (the stored values are unchanged), keeping only whole rows (when the first row alone exceeds the budget, its leading cells are shown), and `schema` lists at most 60 columns within 4 KB. `preview_truncated` and `schema_column_count` (the full column count) appear only when a bound applied, so handles within the bounds are unchanged.
- The `cost-explorer` tool description now tells the agent to verify an empty or $0 result before reporting zero spend, because a wrong filter value or a wrong filter key returns no rows and is indistinguishable from a genuine zero (`"Amazon RDS"` returns nothing because the value is `"Amazon Relational Database Service"`; AWS Marketplace spend returns nothing when filtered on `LEGAL_ENTITY_NAME` because the key for it is `BILLING_ENTITY`). It adds a guideline not to filter on a guessed dimension value, a `REPORTING $0` section covering the filtered and grouped cases, and `BILLING_ENTITY`, `LEGAL_ENTITY_NAME` and `INVOICING_ENTITY` to the dimension reference. `getDimensionValues` returns only values with usage in the period, so the guidance states that a value's absence from it is not proof the value is invalid.
- The Cost Optimization Hub `get_recommendation` not-found warning now explains the likely causes: the ID may not be a Cost Optimization Hub recommendation ID (for example a resource ID or ARN), or the recommendation may no longer exist because recommendations are refreshed daily and removed once they no longer apply. It points to `list_recommendations` to check the resource's current recommendations.
- Cost Optimization Hub `list_recommendations` and `list_recommendation_summaries` now normalize `filters` before calling the API, which is case-sensitive: filter keys match case-, underscore-, and singular/plural-insensitively (`ResourceType` -> `resourceTypes`), enum values match case- and underscore-insensitively (`ec2_instance` -> `Ec2Instance`, `rightsize` -> `Rightsize`), and a single bare value is wrapped in a list. An empty list filter, which the API rejects, now returns a structured `validation_error` naming the filter (and, for enum filters, its accepted values) instead of an `aws_connection_error`. When the API rejects a filter value with `ValidationException`, the response adds `valid_filter_values` for the enum filters sent. The tool description lists all current `resourceTypes` and states these rules.
- The AWS Compute Optimizer tool description now states that `account_ids` accepts at most one account ID per call (as a JSON array, e.g. `'["123456789012"]'`), that two or more are rejected so each account needs its own call, that omitting it returns the caller's own account, and that a management account or delegated administrator sets it to target a member account.
- The `cost-explorer` tool description now documents the filter expression grammar: the leaf shape `{<Dimensions|Tags|CostCategories>: {Key, Values, MatchOptions}}`, the `MatchOptions` that `getCostAndUsage` and `getCostAndUsageWithResources` accept (`Dimensions`: `EQUALS`, `CASE_SENSITIVE`; `Tags` and `CostCategories`: `EQUALS`, `ABSENT`, `CASE_SENSITIVE`), and that the other `MatchOption` values belong to Cost Category rules and anomaly subscriptions. It also documents the time-period limits of `getCostAndUsage`, `getCostAndUsageWithResources`, `getSavingsPlansUtilization`, and the forecast operations, the metrics `getCostForecast` accepts, and that `TAG` can be used as a `GroupBy` type and in `Tags` filter leaves. Documentation only.
- AWS Compute Optimizer `filters` are now normalized for every operation, not only `get_idle_recommendations`: filter keys (`Name`/`Values`), names (case- and singular/plural-insensitive), and values (case- and underscore-insensitive, so a returned `OVER_PROVISIONED` can be passed back as `Overprovisioned`) are folded onto the spelling the API expects, against per-operation tables of accepted values (read from the botocore service model where available). Tag filters are left as given, unrecognized names and values pass through unchanged, and the response echoes the sent filters as `applied_filters`. A bare `Finding` on `get_rds_recommendations` is rejected as ambiguous (use `InstanceFinding` or `StorageFinding`). An `InvalidParameterValueException` now returns a structured error with top-level `error_type`, `operation`, `service`, `request_id`, and `http_status`, and lists `valid_filters` and `submitted_filters` when the service reports a filter problem.
- The AWS Compute Optimizer tool now rejects locally, with a structured `validation_error`, a `max_results` above the API limit (1000, or 100 for `get_idle_recommendations`) and more than one entry in `account_ids` (the API accepts one account ID per request), instead of forwarding them to the API. The legacy `data` payload (including `error_code='MISSING_PARAMETER'`) and messages are preserved for backward compatibility.
- Fixed `invoicing` tool `list_invoice_summaries` validation-error responses missing a structured error type. Its ten local parameter checks (selector, time-filter presence, `billing_period` format and month range, date parsing, reversed/empty range, over-one-month range) returned `format_response('error', ...)` with no top-level classification, so failures surfaced as `UNKNOWN`/`UNKNOWN` in telemetry and could not be told apart from service-side failures. Error responses now carry top-level `error_type='validation_error'`, `operation='ListInvoiceSummaries'`, and `service='Invoicing'`, matching what `handle_aws_error` already attaches to AWS-side errors in the same tool. - Fixed `compute-optimizer-automation` tool error responses missing a structured error type. Its local validation failures (missing required parameters, malformed or account-global-incompatible `regions`, malformed `filters` or unknown filter names, an unsupported `operation`, and a multi-region `next_token` that is malformed, names regions outside `regions`, or is passed to a single-region request) returned `format_response('error', ...)` with `operation` nested under `data` and no top-level classification, so failures surfaced as `UNKNOWN`/`UNKNOWN` in telemetry. They now carry top-level `error_type='validation_error'`, `operation`, and `service='Compute Optimizer Automation'`. Multi-region requests in which no region succeeds previously exposed the failure type only under the region-keyed `data.region_errors.<region>.error_type`; they now also carry a top-level `error_type` (the type every region shares, e.g. `AccessDeniedException` or `ResourceNotFoundException`, otherwise `multi_region_error`), `operation`, and `service`, with `region_errors` kept for per-region detail. The legacy `data` payload and messages are preserved for backward compatibility.
- Fixed `bcm-pricing-calc`, `cost-anomaly`, and `cost-explorer` error responses missing a structured error type. `bcm-pricing-calc` read the AWS message from a non-existent `data.error` key and reported every `get_preferences` failure (including `AccessDenied`) only as `PREFERENCES_NOT_CONFIGURED`; error responses now carry top-level `error_type`, `operation`, and `service`. `cost-anomaly` local input validation (bad date format, `start_date` after `end_date`, a future `end_date`, unknown `feedback`/`total_impact_operator`, missing `total_impact_end`) now carries top-level `error_type='validation_error'`, `operation`, and `service`. `cost-explorer` client-creation failures now carry top-level `error_type='client_creation_error'`, `operation`, and `service`. - Fixed `cost-optimization-hub` local validation error responses omitting a structured error type. The 12 parameter checks that reject a request before calling the API (missing or invalid `group_by`, missing `recommendation_id`, invalid `order_by`, `granularity`, efficiency-metrics dates, and `ranking_mode`, and unsupported operations) returned `format_response('error', ...)` with no top-level `error_type`/`operation`/`service`, so they surfaced without a classifiable type. The legacy `status`/`data`/`message` payload is preserved for backward compatibility.
- Fixed the AWS Compute Optimizer `get_idle_recommendations` operation rejecting `ResourceType` and `Finding` filter values whose casing differs from the idle enums (e.g. `EbsVolume` instead of `EBSVolume`, `idle` instead of `Idle`). Passed values are now normalized case-insensitively against the idle enums read from the installed botocore service model, and the response echoes the normalized filters as `applied_filters`. An `InvalidParameterValueException` now returns a structured error listing `valid_resource_type_values` and `valid_finding_values` so callers can self-correct instead of retrying the same request.
- Fixed SQL offload failing with `database is locked` when several tool calls offload responses at the same time. `convert_api_response_to_table` inserted the table's `schema_info` row after committing the data and then awaited a log call with that write transaction still open. A concurrent conversion on the same event loop then blocked on the lock: SQLite's busy timeout waits synchronously, so the holder never resumed, and the second conversion failed after `BCM_MCP_SQLITE_TIMEOUT_MS` (30 seconds by default) and returned the raw response instead of a table. The uncommitted `schema_info` row was also rolled back when the connection closed, so offloaded tables were never registered there. The row is now committed before the await.
